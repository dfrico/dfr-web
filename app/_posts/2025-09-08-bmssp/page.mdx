*Written in September 2025 as the start of a [short series](https://0xdf4.bearblog.dev/blog/). Corrected and finished in November 2026: see the update at the end.*

A few weeks ago I read [an interesting paper](https://arxiv.org/abs/2504.17033) titled "Breaking the Sorting Barrier for Directed Single-Source Shortest Paths" (Duan, Mao, Mao, Shu and Yin, 2025). Shortest path algorithms are everywhere: GPS apps, network routing, game AIs... and since the 80s, the best known bound for the general case (directed graphs, non-negative weights) was Dijkstra's algorithm with a Fibonacci heap. This paper beats it, with an algorithm called **BMSSP** ("Bounded Multi-Source Shortest Path").

"Beats" here means the bound: as graphs get bigger, BMSSP's running time grows more slowly than Dijkstra's. That's a statement about very large $n$, with constant factors ignored. It doesn't promise that BMSSP is faster on any graph you'd actually run it on.

I wanted to write about it and implement it, but there are a few prerequisites for understanding the paper, and covering them all in one post would be too much. So this is the start of a short series, going from Dijkstra to BMSSP one prerequisite at a time: a refresher on Dijkstra, then the two pieces BMSSP borrows, edge relaxation and Bellman-Ford.

Throughout the post, $n$ is the number of vertices and $m$ the number of edges, like in the paper.

## A quick Dijkstra refresher

Dijkstra finds single-source shortest paths: the shortest distance from one node $s$ to every other node, in a graph with **non-negative** edge weights[^1].

```python
import heapq

def dijkstra(graph, start):
    dist = {node: float('inf') for node in graph}
    dist[start] = 0.0
    pq = [(0.0, start)]
    visited = set()

    while pq:
        d, u = heapq.heappop(pq)
        if u in visited:
            continue
        visited.add(u)
        for v, w in graph[u]:
            if v not in visited and d + w < dist[v]:
                dist[v] = d + w
                heapq.heappush(pq, (dist[v], v))

    return dist
```

It keeps three things:

1. `pq` is a priority queue (a min-heap, `heapq` in Python) with the nodes we've reached but not finished yet. This is the **frontier**, and it's going to be important later.
2. `visited` is the set of finished nodes.
3. `dist` is our best known distance to each node. Everything starts at $\infty$, except the source, at $0$.

Then it runs the "extract min" loop: take the closest unfinished node, mark it as finished, and update its neighbours. The key assumption is that when a node comes out of the queue, its distance is final: with non-negative weights, nothing we find later can make it shorter. (This version skips the predecessor array, which you'd need to rebuild the actual path, since we only care about distances.)

Notice the stale entries like `(4, 'B')`: instead of updating a node's position in the heap, we push a new entry and skip the old one when it comes out. It's the simplest way to do it with `heapq`.

### Where the cost comes from

Each node is finished once, and each edge pushes at most one entry, so with a binary heap Dijkstra runs in $O(m \log n)$[^2]. With a Fibonacci heap it's $O(m + n \log n)$, the bound that stood for decades (though in practice it's rarely worth it[^3]).

The $n \log n$ term comes from the order in which Dijkstra finishes nodes: A, C, B, D, E, F, which is every node **sorted by distance**. On top of computing the distances, Dijkstra sorts the nodes by them, and sorting $n$ values by comparing them costs $n \log n$. That's the **sorting barrier**[^4].

The paper gets around it because we never asked for the order, only for the distances. BMSSP computes the distances without fully sorting the nodes, in $O(m \log^{2/3} n)$. To see how, we need two more pieces.

## Edge relaxation

Dijkstra repeatedly performs this operation:

```python
if d + w < dist[v]:
    dist[v] = d + w
```

This is called **edge relaxation**: check whether going through $u$ and then taking the edge $u \to v$ beats our current best distance to $v$, and if it does, update it. As a formula, $d[v] = \min(d[v],\ d[u] + w(u,v))$. Think of it like this: distance estimates start too high ($\infty$) and gradually "relax" down toward their true values. They never go up.

Why does this work? The true shortest distances satisfy $dist(v) \le dist(u) + w(u,v)$ for every edge: the best route to $v$ can't be longer than the best route to $u$ plus one more edge. If an edge breaks that rule with our current estimates, our estimate for $v$ is wrong, and relaxing the edge fixes exactly that. When no edge breaks it, we're done. (Careful: this is not "the direct route is always shorter". In the graph above, the direct edge $A \to B$ costs 4, and the detour $A \to C \to B$ costs 3.)

Pretty much every shortest path algorithm is built on this rule. What changes between them is **which edges they relax, and in what order**. Dijkstra picks them very carefully, using the heap. Bellman-Ford doesn't pick at all.

## Bellman-Ford

```python
def bellman_ford(graph, start):
    dist = {node: float('inf') for node in graph}
    dist[start] = 0.0

    # Relax every edge, up to n - 1 times
    for _ in range(len(graph) - 1):
        updated = False
        for u in graph:
            for v, w in graph[u]:
                if dist[u] + w < dist[v]:
                    dist[v] = dist[u] + w
                    updated = True
        if not updated:
            break

    return dist

print(bellman_ford(graph, 'A'))
# {'A': 0.0, 'B': 3.0, 'C': 2.0, 'D': 8.0, 'E': 10.0, 'F': 13.0}
```

The first thing you'd notice if you open them side by side is the missing `heapq` import. Bellman-Ford doesn't prioritise anything: it relaxes **every edge**, in rounds, up to $n - 1$ times[^5], and stops early if a whole round changes nothing. That's $O(nm)$, much slower than Dijkstra. It's usually taught because it handles negative edges, which Dijkstra can't[^6], but BMSSP only works with non-negative weights, so that's not why we need it here.

We need it for this property: **after $i$ rounds, every node whose shortest path has at most $i$ edges already has its correct distance.** Bellman-Ford finishes nodes by number of hops, not by distance, and it doesn't need to sort anything to do it.

The work can also be cut short in two ways: run only $k$ rounds instead of $n - 1$, or ignore any distance above some cap $B$. BMSSP does both, and the next post in the series was going to start there, with a bounded version of Dijkstra.

### How BMSSP works

BMSSP uses both algorithms, but bounded, with the two knobs from above:

- **$k$, a step limit.** Run only $k$ rounds of Bellman-Ford, or stop Dijkstra after it finishes $k$ nodes.
- **$B$, a distance cap.** Ignore any relaxation that would give a distance of $B$ or more.

They're easy to mix up: $k$ counts edges, and $B$ caps distances. Bounding the work like this lets BMSSP split the problem into small pieces and never sort all the nodes at once.

Dijkstra's problem is the frontier: every node goes through one big heap, and every extract-min costs $\log n$. BMSSP keeps the frontier small, and splits the work by distance. Its recursive function solves a "bounded multi-source" problem, hence the name: given a set of frontier nodes $S$ and a cap $B$, find the true distance of every node closer than $B$ whose shortest path goes through $S$. The top-level call is $S = \{s\}$ and $B = \infty$, which is just regular single-source shortest paths.

Each call does four things:

1. **Shrink the frontier (FindPivots).** Run $k$ rounds of Bellman-Ford from $S$, capped at $B$. Everything within $k$ hops of $S$ is now done. Then look at the shortest-path trees hanging from each node in $S$: a tree with fewer than $k$ nodes is already finished. Only the roots of big trees stay. Those are the **pivots**, and there are about $k$ times fewer of them than nodes Bellman-Ford touched.
2. **Split by distance and recurse.** Put the pivots into a priority structure $D$. Pull out the closest ones, along with a bound $B_i$ that separates them from the rest, and recurse one level down with cap $B_i$. Relax the edges of the nodes the sub-call finished: anything that lands in $[B_i, B)$ goes back into $D$ for later. Repeat until $D$ is empty.
3. **Base case.** At the bottom, there's a single source. Run a small Dijkstra from it, and stop after $k + 1$ nodes.
4. **Stop early.** Each level has a budget of nodes. When a call fills it, it stops and reports how far it got, and the caller picks up from there.

Very roughly, instead of one big sort over all $n$ nodes, BMSSP does many small sorts over frontiers that FindPivots keeps shrinking, and the paper's special data structure for $D$ makes those small sorts cheap. That's intuition, not a proof. The proof is sections 3 and 4 of the paper, and it's dense.

### My Python implementation

My implementation (linked at the end) is about 200 lines of Python, and it simplifies the paper in two big ways:

1. **A plain heap instead of the paper's data structure $D$** (Lemma 3.3). Same interface, worse complexity. This is the big one: without it, we don't get the paper's bound. It's still correct.
2. **No constant-degree transformation.** The paper rewrites the graph so every node has at most two incoming and two outgoing edges. That matters for the analysis, not for correctness.

I tested it the simple way: run Dijkstra and BMSSP on the same graph and compare every distance. I ran it on 3,000 random directed graphs with 1 to 4,096 nodes and either real-valued or small integer weights, plus 2,000 graphs where most or all edges weigh zero, and every distance matched. That doesn't prove it's correct: random graphs won't catch a bug that only shows up on some structure they don't produce.

Getting there took two bug fixes, and both were about ties.

### Two tie-breaking bugs

The paper assumes that all path lengths are different, and handles ties by comparing paths as tuples, not just their lengths. It's easy to skip, so I did. The first version compared plain distances, and it passed every test with random real-valued weights (where ties basically never happen). With small integer weights it got wrong answers on 68 out of 200 graphs.

The suspect is `pull`, the operation that takes the closest nodes out of $D$. It has to return a bound that's **strictly** above every node it pulled and at or below every node it left. With ties, two nodes at the same distance can end up on opposite sides of the bound. Comparing `(distance, node id)` instead of distances gives every node a unique key, and that fixed all 200 graphs.

That fix wasn't enough. On graphs with zero-weight edges, BMSSP didn't give wrong answers: it never finished. Take a zero-weight edge from node 7 to node 1. Both end up at the same distance, and node 1 gets the *smaller* key, even though it comes after 7 on the path. The base case starts from 7, finds 1, and returns the largest key it saw as the new bound. That's 7's own key, so 7 isn't "done" and goes back on the frontier. Then it gets pulled again, and the same thing happens, forever.

The algorithm relies on following an edge always giving a bigger key. Positive weights guarantee that, but zero weights don't (the paper's whole-path comparison does). Adding the hop count in the middle is enough to get it back, because a zero-weight edge adds nothing to the distance, but it always adds one hop:

```python
def key(self, v):
    """Order vertices by (distance, hops, id) so no two keys are ever equal."""
    return (self.dist[v], self.hops[v], v)
```

Castro, Clementino and de Freitas, who implemented the full algorithm in C++ (more on that below), use the same kind of key: length, then hop count, then vertex, then predecessor[^7]. The paper's authors also start their 2026 follow-up (below) by defining a tie-breaking rule for distance labels. BMSSPy uses (length, path size, edge id), and its paper gives the original paper's own key as (length, path size, u, v): the hop count was in the paper all along, and it's exactly the part I skipped.

### Is it faster?

No. On random sparse graphs (average degree 4), my version is about 3× slower than Dijkstra at 100K and 1M nodes (16 s against 5.5 s at a million, on an M1 Pro), and it does 2–3× more edge relaxations. Most of the extra relaxations come from FindPivots' Bellman-Ford rounds and from the recursion relaxing the same edges again at each level.

In hindsight, that's the result to expect, for two reasons. First, my version has no $D$, so every frontier operation still costs $\log n$, like in Dijkstra, and BMSSP does more of them. It tests the algorithm's structure and its correctness, not the theorem. Second, the theoretical win is small: compared to Dijkstra with a binary heap, it's a factor of $\log^{1/3} n$, about 2.7 for a million nodes, and BMSSP's overhead easily costs more than that. Even the parameter $k$ that controls how much FindPivots shrinks the frontier is stuck at 2 until $n = 2^{27}$, about 134 million nodes.

Better evidence comes from people who went further than I did:

- **Castro, Clementino and de Freitas** implemented the full algorithm, including $D$, in C++. Dijkstra was 3–4× faster in every scenario they tested: random sparse graphs, grids and US road networks. On their largest random graphs ($2^{25}$ vertices, about 33 million), BMSSP took about 84 s against Dijkstra's 22 s. They estimate the number of vertices would have to vastly exceed $10^{67}$ for their worst-case implementation to win.
- **Rohan Paranjpe** implemented it in Rust, with a walkthrough of the algorithm on his blog. On road networks around DC and Northern California it ran 5–7× slower than Dijkstra.
- **Valko, Paranjpe and Marx Gómez** extended that Rust version and tested it on Lightning Network snapshots. In the best case, BMSSP took nearly twice as long as Dijkstra.
- **Makowski, Guter, Russell, Castro and Saragih** (MIT Center for Transportation & Logistics, plus Lucas Castro from the C++ paper) published BMSSPy, a pure-Python package that implements the paper faithfully. It's the closest comparison to mine. On large grids it beat NetworkX's and igraph's Dijkstra (by 1.6–2.1× and 2.4–4.2×), but an optimized Dijkstra from their SCGraph library was about 14× faster on a million-node grid and about 30× faster on their largest road network. They put the break-even at about $5 \times 10^{22}$ nodes plus edges.

My 3× in Python is in line with these results, including the complete C++ implementation. BMSSP shows that shortest paths don't have to pay for sorting, at least in theory. In practice, on any graph you're likely to run, Dijkstra with a binary heap is still faster.

The theory kept moving, though. In February 2026, Duan, Mao, Shu and Yin published [a faster algorithm](https://arxiv.org/abs/2602.07868), $O(m\sqrt{\log n \log\log n})$ on sparse graphs (ICALP 2026). It builds on the same BMSSP recursion and makes finding pivots cheaper. I haven't tried implementing it.
